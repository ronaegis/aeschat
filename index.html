About AESchat

Features:
- Fast and easy way to securely chat
- No server: messages travel directly from browser to browser (WebRTC)
- End-to-end encryption done in the browser
- Uses bcrypt, SHA256 and AES-GCM
- Encryption key derived from the room name using bcrypt
- No message stored anywhere, history comes from the people in the room
- Source code at GitHub
- Easy to generate link addresses for other people to join

Good to know:
- People in the same room can see each other's IP address
- Public relays are only used to introduce browsers to each other
- Pick a random room name: anyone who guesses the name can join

How it works without a server

AESchat is a set of static files. Nothing runs on the host that serves this page: there is no chat server, no database and no account. Your browser does all the work and talks straight to the other browsers in the room.

  1. The room name becomes keys. Your browser turns the room name into a room id and two secret keys. The name itself never leaves your browser.
  2. Browsers find each other. Two browsers cannot connect without an introduction, so each one posts a short encrypted connection offer to a few public Nostr relays, using Trystero. Nobody involved with AESchat runs those relays, and they never receive a chat message.
  3. They connect directly. Once introduced, the browsers open a WebRTC data channel between themselves. From then on every message travels from browser to browser, with nothing in the middle.
  4. History comes from the room. When you join, someone already in the room hands you the last 32 lines. Nothing is stored anywhere else: when the last person closes the page, the conversation is gone.

The encryption in detail

Everything is done in your browser with its built-in cryptography (WebCrypto), plus bcrypt in JavaScript.

From room name to keys

h         = bcrypt(room name + "AESchat!", cost 10, fixed salt)
room id   = SHA-256(h)
handshake = SHA-256(h + room id + "signal")
chat key  = SHA-256(h + room id)             256-bit AES key
  • bcrypt is slow on purpose (1024 rounds), which makes guessing room names expensive.
  • The room id is what browsers use to find each other. It cannot be turned back into the room name or the keys.
  • The chat key is held by the browser as a non-extractable key and is never sent anywhere.

Three layers protect a message

  1. Message encryption. Each chat line, each username and the history are encrypted with AES-256-GCM using the chat key and a fresh random 96-bit nonce. GCM also authenticates: a message that was modified, or encrypted with another key, is rejected.
  2. Connection encryption. The WebRTC channel between two browsers is encrypted with DTLS using keys made for that connection only. Each browser also creates a throwaway ECDSA P-256 identity per session, and Trystero checks it against the connection's certificate so nobody can sit in the middle.
  3. Handshake encryption. The connection offers posted to the relays are encrypted with AES-256-GCM, using a key stretched from the handshake password with PBKDF2-SHA256 (600,000 rounds). Without the room name, a relay can neither read an offer nor join the room.

Choosing a good room password

The room name is both the address of the room and its password, so it has to be hard to guess, not easy to remember. The safest choice is the Random button, which picks six words with your browser's secure random generator. If you make your own, use at least six unrelated words or 14 random characters, and avoid anything a person or a program could guess: names, dates, places, song or film quotes, keyboard patterns, or a password you use elsewhere. Use a new room for each conversation, since anyone who ever had the name can come back. Send the name or the "Share room" link only through a channel you already trust, and never post it in public: the link contains the room name, so whoever sees the link can join.

Limits you should know

  • The room name is the only secret. Anyone who knows or guesses it can join and read. The Random button makes a six-word name with about 65 bits of randomness; share it through a channel you trust.
  • The chat key never changes. Every message in a room uses the same key, for as long as the room name is used. A conversation recorded off the network still stays protected if the name leaks later, because each direct connection also has its own one-time DTLS keys.
  • The bcrypt salt is fixed, so a short or common room name can be guessed from its room id. Do not use one.
  • Direct means visible. People in the same room can see each other's IP address.
  • You trust the page. Like any web app, whoever serves these files could change them. The source is small enough to read and to host yourself.
